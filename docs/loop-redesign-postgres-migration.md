# Colony Loop → Railway + Postgres: Redesign-First, Parallel-Run Migration Plan

*Started 2026-08-02. This is the spine for moving the automation loop off the Mac
Mini onto a managed cloud host with a durable Postgres queue — done as a
**reevaluation**, not a lift-and-shift, and executed **side-by-side** so the
current system stays live until the new one is bulletproof.*

## The rules (Teddy, 2026-08-02)
1. **Reevaluate + tighten before we move.** Don't carry the cruft/bad ideas onto Postgres. The migration is the forcing function to prune and fix.
2. **Run side-by-side.** The current system stays 100% live as the safety net. Build the new stack alongside it. **We do not move over until it's bulletproof.** Worst case = we're exactly where we are today.
3. **Never delete the old one at cutover** — it becomes the instant hot-rollback, decommissioned only after the new one is proven.
4. **Exactly one system ACTS (sends/calls/writes) at a time.** Two live actors = double-texts; two loops draining one queue = clobbered work. The new stack runs in **shadow (dry-run)** until the flip.

---

## Where we are today (audit facts, from the code — 2026-08-02)
- **556 agent files** in `colony-loop/agents/`; registry maps ~503 signal→file entries.
- **Only 127 are actually reachable/LIVE:** **69 reactive** (fired by a real event) + **58 scheduled** (fired by the tick timer).
- **~429 are dead:** ~376 half-wired (registered, no producer) + ~53 dormant (not even registered — the whole `scout_request_*` family, etc.). Almost all auto-generated by COLONY_ARCHITECT from the blueprint and never wired to an event.
- Loop runs a **120s tick**; queue defaults to **Xano** (`get_pending_colony_signals` + `event_log` dedup-scan every 2 min ≈ the ~34k Xano-writes/day + past 502/melt incidents). Local SQLite (`db.js`, `node:sqlite`) is built + better but opt-in.
- **~35 Netlify crons already exist** (Gmail pollers, sweeps, digests). The loop-vs-cron boundary is blurry — the loop does a lot of pure clock-driven work that has no in-process state.
- Mac-only anchors: 9 `launchd` plists (hardcoded `/Users/tpivacek`, `/opt/homebrew/bin/node`), a `caffeinate` plist, and the **Marcone parts browser daemon** (`parts/serve.js` — headful Playwright Chromium with on-disk login cookies + a local tunnel) = the least cloud-portable piece.

## Redesign principles (the lens for what survives)
1. **Dead weight doesn't travel** — no trigger + no consumer = delete, don't migrate.
2. **Right home for each job** — pure timer jobs → cloud crons; the loop keeps *only* reactive/stateful chains.
3. **One write, many reads** — every fact born once; kill re-keying/marker-mismatch bugs.
4. **Make old bugs structurally impossible** — Postgres queue with idempotency keys + `SKIP LOCKED`; all sends through one guarded path.
5. **Observable from birth** — every agent run + send traced.
6. **Zero Mac-isms** — no launchd/local-FS/host-awake assumptions.

5. **Terminal "insight" dead-letter emits** — SCHEDULING_DECISION, RECRUITING_INSIGHT, PERFORMANCE_INSIGHT, HVAC_INTELLIGENCE, CUSTOMER_INTELLIGENCE, MARKET_INTELLIGENCE, CONTENT_GENERATED, etc.: emitted by ~200 call-sites, consumed by nobody → pure `no_agent_yet` queue churn. ### MERGE (collapse redundant paths)
7. **EOD digests → one job.** DAILY_REVENUE_SUMMARY + TECH_EOD_REPORT + OFFICE_EOD_SUMMARY + TDR_COMPLETENESS_REPORT + TECH_ASSIST_EOD_REPORT + cron `scorecard-digest` all fire 6-9pm.
8. **Parts-arrival → one pipeline.** `netlify/parts-arrival-watch.js` + loop PARTS_ARRIVAL_CHECK + `mark_parts_arrived_POST.xs` + `parts-vendor-gmail-poller` = 4 code paths for one event.
9. **SMS-escalation logic → one helper.** ~49 agents emit CUSTOMER_SMS_REPLY and ~46 emit CUSTOMER_SMS_ESCALATE with copy-pasted blocks.
10. **Late/stuck detectors → one.** TECH_LATE_CHECK + SCHEDULER_BEHIND_CHECK + STUCK_JOB_DETECTOR + TECH_RUNNING_LATE_SCAN + cron `tech-missed-stop-check` overlap. (Also: `multi-appliance-split-sweep` vs `multi-machine-watch` = two sweeps for one problem.)

### FIX (before/at migration)
11. **DB-as-queue → real Postgres queue.** Adopt `db.js`'s good ideas directly: `process_after` deadline (kills per-tick re-emit of future signals), `fired_markers UNIQUE(action, day_key)` dedup, `inbox_ref` idempotency, and add `SELECT … FOR UPDATE SKIP LOCKED` claiming.
12. **Server-side emit idempotency** — dedup is currently check-then-emit in JS; overlapping producers (loop + cron + Xano) can double-emit. A `UNIQUE dedup_key` at insert makes double-fire impossible.
13. **Single-write / marker-mismatch bugs** — documented storms came from the marker *written* (`*_emitted`) ≠ marker *checked* (`*_fired`/`*_sent`): TECH_EOD_REPORT ~1,300 texts/day, DAILY_TECH_BRIEFING per-tick re-fire, healthcheck 2-day SMS spam. **Standardize one marker name per scheduled signal.**
14. **Move dedup + event_log to Postgres TOO — not just the queue.** ⚠️ Correctness note from the audit: `store.js` today keeps dedup/event_log on Xano even in local mode. If we move only the queue and leave dedup on Xano, a Xano outage still breaks dedup and can re-storm. **Queue + dedup + event_log move together.**
15. **Kill Mac-isms** — the 9 launchd plists → container/systemd units; drop `caffeinate`; healthcheck reads Xano token from `~/.xano/...` + writes state to `os.homedir()` → env/secret paths.
16. **Marcone parts browser daemon** — the one genuinely hard-to-move piece. Decide: (a) rely on the live **mSupply/Marcone API** (already working per CLAUDE.md) and retire the browser daemon, or (b) run headless Playwright in a container, or (c) leave it on a small dedicated box. Recommended: (a) if the API covers lookups.

### CARRY 1:1 (reliability guards — do not regress; they exist because of real incidents)
- **SMS circuit breaker** (`sms.js:14-59`, global cap `SMS_BREAKER_MAX`/window) — the 15k-text backstop.
- **Quiet-hours** (9pm-8am CT) + **tech weekend hard-mute**.
- **Tech-SMS allow-list** + **owner-SMS canceled→portal**.
- **`customerOutreachSinceMs` forward-only cutoff** + **2-text intake cap**.
- **Phone pause switch + heartbeat over Netlify/Supabase** (deliberately NOT Xano, so it survives a Xano melt).
- **Over-emission dedup** (fail-closed) — becomes the Postgres UNIQUE key.
> All sends route through **one guarded path**; the breaker/quiet-hours/caps live there, not scattered.

## Phase 1 — Tighten in place (on the CURRENT system — safe, improves what's already live)
Do the cleanup *before* moving, so we migrate a lean, correct system:
1. Archive the ~429 dead agents (reversible), keep `validateRegistry()` green.
2. Move pure timer jobs (the LEAN-excluded BI/analytics/watchdog set + daily digests) from loop-timer → **Netlify crons**. This shrinks the loop toward its reactive core and removes host dependency from those jobs immediately.
3. Apply the MERGEs (EOD, parts-arrival, SMS-escalation, late/stuck).
4. Fix the marker-name single-write bugs (#13).
5. **Result:** the "loop" that even needs to move is a small reactive/stateful core, not 556 files.

## Phase 2 — Build the new stack in SHADOW (Railway + Postgres)
- **Postgres queue schema** (draft):
  ```sql
  create table loop_signals (
    id            bigint generated always as identity primary key,
    signal_type   text not null,
    payload       jsonb not null default '{}',
    trace_id      text,
    dedup_key     text unique,                              -- idempotent emit
    process_after timestamptz not null default now(),       -- future signals sleep
    status        text not null default 'pending',          -- pending|processing|done|dead
    attempts      int not null default 0,
    source        text,                                     -- loop|cron|tee|agent
    created_at    timestamptz not null default now(),
    processed_at  timestamptz
  );
  create index on loop_signals (status, process_after);
  create table loop_fired_markers (               -- scheduled dedup, one per (action, day)
    action text not null, day_key text not null,
    fired_at timestamptz not null default now(),
    primary key (action, day_key)
  );
  create table loop_events (                       -- event_log off Xano (audit + observability)
    id bigint generated always as identity primary key,
    action text not null, job_id bigint, actor text,
    meta jsonb default '{}', created_at timestamptz not null default now()
  );
  create index on loop_events (action, created_at);
  ```
  Worker claim: `UPDATE loop_signals SET status='processing', attempts=attempts+1 WHERE id IN (SELECT id FROM loop_signals WHERE status='pending' AND process_after<=now() ORDER BY id FOR UPDATE SKIP LOCKED LIMIT n) RETURNING *;`
- **`store.js` gets a `pg` router** alongside `local`/`xano` — queue **+ dedup + event_log** all on Postgres (fixes #14).
- **Tee the event stream:** the current live system's emits are *mirrored* into the PG queue (read-only copy). The shadow **never drains the live Xano/local queue** — it can't steal or clobber the old system's work.
- **Deploy on Railway:** `railway.json` already sets NIXPACKS + `node index.js` + root `colony-loop`. Add `DRY_RUN=true`, `COLONY_NAME=cloud-shadow`, `LOOP_STORE=pg`, Postgres connection (Supabase). The shadow runs the *redesigned* (lean) agent set, computes what it WOULD do, logs every decision to `loop_events` — **sends/calls/writes disabled**.

## Phase 3 — Validate: shadow diff → "bulletproof"
- **Decision-diff harness:** for each event, compare the shadow's would-do decision against what the live system actually did. Track a per-critical-path match rate.
- **"Bulletproof" bar (not a vibe):** shadow decisions match live actions ~100% across **every** critical path (greeting, scheduling, warranty, parts, invoicing, sends) for **N consecutive days**, all reliability guards proven under real load, observability green, and the queue proven idempotent (no double-fire) under a replay test.

## Phase 4 — Flip + retain rollback
1. **Confirm the old system is the only actor** right up to the flip.
2. **Flip = a toggle:** set the Railway stack `DRY_RUN=false` and **pause the old system's acting** in the same step. Exactly one actor.
3. **Old system = hot rollback** for a cooldown period (reverse the toggle to roll back in ~1 min). Decommission the Mac loop only after sustained confidence.
