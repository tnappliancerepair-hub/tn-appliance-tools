## 1. Rotate `XANO_METADATA_TOKEN` to a workspace-scoped key

**Why:** Current `XANO_METADATA_TOKEN` in Netlify is the full account-scoped Xano JWT (~3.3 KB on its own, 78% of the AWS Lambda 4 KB env-var ceiling). Two problems flowing from that:
1. **Deploy blocker** — any function deploy now bounces with `Your environment variables exceed the 4KB limit imposed by AWS Lambda` (hit live tonight when trying to ship `send-teddy-sms.js`).
2. **Security blast radius** — the JWT currently carries `tenant_center:*`, `tenant_cluster:*`, `release`, every `workspace:*` scope including `secrets`, `datasource:live`, and `workflow_test`. `metadata-crud.js` actually uses `workspace:content` only. The stopgap was always supposed to be temporary per `netlify/functions/_lib/xano/metadata-crud.js:15-18`.

**How:**
1. Xano UI → Account / Settings → **Personal Access Tokens** (or **Metadata API keys**) → New token.
2. Scope: `workspace:content:read` + `workspace:content:edit` only. Nothing tenant-level. Nothing secrets.
3. Name it something like `netlify-metadata-crud-2026-05-21`.
4. Copy the new token (you'll only see it once).
5. `netlify env:set XANO_METADATA_TOKEN <new-value> --context production --scope functions runtime`
   - Drop `builds` and `post-processing` scopes — they don't need it, and trimming saves a few bytes.
6. `netlify env:get XANO_METADATA_TOKEN` to confirm.
7. Smoke-test by hitting any Netlify function that imports `metadata-crud.js` (e.g. trigger a tech-sms onboarding flow) — should still find techs / log events normally.

**Expected new size:** ~150-200 bytes (scoped keys are much smaller than account JWTs). Frees ~3 KB.

## 3. HCP phone normalization to E.164

**Why:** Tonight's `feedback_reply_webhook` verification exposed an orthogonal bug. All 3,300+ customer rows in Xano store `phone` as bare 10-digit (e.g. `6154855795`), because that's how HCP intake writes them. But the webhook (and any future Twilio-driven webhook) compares against `$input.From`, which Twilio sends as E.164 (`+16154855795`). Result: every HCP-sourced customer fails the customer lookup in feedback_reply_webhook, even after tonight's dedup fix. Tonight's verification only worked because we created the test customer in E.164 manually.

**Decision needed before doing anything:**
- **Forward-fix only** — change the writer (`hcp_job_webhook` lines 256-261 + any other intake path) to normalize incoming phones to E.164 before insert. Historical 3,300 rows stay bare. Means feedback_reply only works for new customers going forward; existing customers' replies still miss. **Pro:** zero-risk on historical data. **Con:** leaves a long tail of dead lookups.
- **Forward-fix + backfill** — same writer change, plus a one-shot backfill task that rewrites the existing 3,300 rows from `6154855795` → `+16154855795`. **Pro:** fixes everyone in one go. **Con:** need to be careful about phones that are blank, malformed, or already-E.164 (we found none with `+` tonight, but worth a defensive check).
- **Read-time normalization** — leave the column as-is, normalize at the webhook query layer (compare both bare-10 and E.164 forms). **Pro:** no migration. **Con:** every webhook needs to know about both formats forever.

**Recommendation:** Forward-fix + backfill. Cleanest steady state. The backfill is a simple `db.query customer where phone NOT LIKE '+%'` → `db.edit phone = "+1" ~ phone` loop. Skip blanks.
